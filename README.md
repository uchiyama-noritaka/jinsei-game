# 人生（終盤）ゲーム ─ 第1〜2章

介護・終活をテーマにした、LINE風メッセージ画面で進むノベルゲーム。
企画書の「開発ロードマップ W1: 土台構築」にあたる第1章（日常編）に続き、
第2章（予兆編）まで通しで遊べる。ステータスは章をまたいで引き継がれる。

## 遊び方

```bash
npm install
npm run dev
```

表示されるURL（通常 http://localhost:5173）をブラウザで開く。

## ビルド

```bash
npm run build
```

`dist/index.html` に、JS・CSSをすべて1ファイルに埋め込んだ自己完結型のHTMLが出力される（`vite-plugin-singlefile`を使用）。この1ファイルをそのままどこにでも置けば動く。

## 収録している章

| 章 | タイトル | 内容 |
| --- | --- | --- |
| 第1章 | 日常編 ── 「元気だよ」の一言から | 母からの何気ないLINE。息切れ、置き忘れ。まだ「歳のせい」で説明がつく |
| 第2章 | 予兆編 ── 「気のせい」が効かなくなる | 同じ話の繰り返し、空焚き、深夜の徘徊。隣人と兄が会話に入ってくる |

第2章のエンディングは3種類（`向き合いはじめた夜` / `あなただけが頼りよ` / `見ないふりをした夜`）。
第1章から持ち越した「知識」と「母との関係」が、そのまま結末の分かれ目になる。

## 何を・なぜこの設計にしたか

- **シナリオをコードから分離した（`src/data/chapter1.ts`, `chapter2.ts`）**
  ノード（発言のかたまり）と選択肢をデータとして定義し、エンジン（`src/store/gameStore.ts`）はそれを読んで進行を管理するだけにした。章を追加するときはデータファイルを1つ足し、`src/data/chapters.ts` の登録簿に並べて、前の章の `nextChapterId` を向けるだけでよい。UIやロジックには触らない。

- **「選んだ内容への返事」は選択肢側に持たせた（`choice.reply`）**
  最初は「選択肢 → 次のノード本文」しか無かったため、次のノードの1行目が特定の選択肢を前提にした返事になり、肯定的に答えたのに「あら、そうだった？」と返るような噛み合わない会話が生まれていた。いまは、選んだ内容に噛み合う返事はすべて選択肢の `reply` に置き、ノード本文はどの選択肢のあとに読んでも成立する内容だけにしている。**意思疎通が怪しくなる演出をやるときは、`reply` に意図してそう書く**（事故ではなく演出として出す）。この約束は `npm run check:scenario` で機械的に検査していて、`reply` の無い選択肢があると落ちる。

- **エンディングもデータにした（`endings`）**
  第1章の時点では「bondMotherがしきい値以上か」をエンジン側にベタ書きしていたが、章ごとに結末が増えると破綻するので、`条件 → 結び` の配列として各章に持たせた。上から順に判定し、最初に条件を満たしたものを採用、条件を持たない最後の1件がフォールバックになる。分岐条件を読むのにコードを開かなくてよくなった。

- **選択肢に解禁条件をつけた（`requires`）**
  第2章の「地域包括支援センターに相談してみる」は、知識5以上でないと選べない。第1章から母の変化に気づいて言葉にしてきたプレイヤーにだけ道が開く、という設計。条件を満たしていない選択肢は消さずに、破線＋「知識 5 以上 で選べる」の一文で見せている。何を積めば違う結末に届くのかが、プレイ中に伝わるようにするため。

- **会話相手を章の途中で切り替えられるようにした（`speaker`）**
  第2章では隣の田中さん・兄とのやり取りが挟まる。ノードに `speaker` があればヘッダーの名前とアイコンが差し替わり、`tone` を指定すると画面の地の色も変わる。文字を読む前に「場面が切り替わった」と気づけるようにするため。色はどれも紙が差し替わった程度の差にとどめ、ライト/ダークの両方で定義している。

  切り替えのタイミングは、現在ノードではなく **表示済みの最後のメッセージ** に追従させている（各メッセージが「誰との会話か」を持っている）。現在ノードを見てしまうと、選択肢をタップした瞬間に相手が変わり、自分の発言や母からの返事が、次の相手のトーク画面に表示されているように見えてしまうため。

- **数字はスロットのように回して止める（`StatusHUD`）**
  選択でステータスが動いたとき、桁ごとのリールが1周まわって左の桁から順に止まり、動いたぶんが「+3」「−8」と一瞬だけ数字の上に出る。**この選択が数字を動かした**と目で結びつけてもらうため。ストアは `choice.effects` ではなく前後の差（`lastDelta`）を渡していて、0や100で頭打ちになったときに動いていない数字を「+4」と表示してしまわないようにしている。読み込みや章の移動では演出を出さない（操作の結果ではないため）。アニメーションを切っている環境では、回さずに結果だけを出す。

- **地の色は白を使わない**
  画面の地を白にすると、相手の吹き出し（白）が地に溶けて境目が見えなくなる。地はどの場面でも少し色のついた紙にして、吹き出しを浮かせている。文字色のコントラストは主要な組み合わせを実測して決めた（小さい文字に使う暖色は、白地で3.05しか出ていなかったため4.87まで落としている）。

- **状態管理はZustand**
  `stats`（お金・気力・母/きょうだいとの関係値・知識）と `timeline`（表示済みメッセージ）、`chapterId` と `currentNodeId`（今どの章のどこにいるか）をシンプルなストアで一元管理している。

- **セーブはlocalStorageへ自動保存**
  選択するたびに`persist()`が状態をlocalStorageへ書き込む。サーバーもログインも不要で、ブラウザを閉じても続きから再開できる。章をまたぐ形式に変えたためキーは `jinsei-game-save-v2`。読み込み時に章IDとノードIDの実在を確認し、シナリオを書き替えたあとの古いセーブで詰まないようにしている。

- **ビルドを1ファイルに固めた（vite-plugin-singlefile）**
  MVPの段階では「どこでもすぐ動かせる」ことを優先。章が増えてバンドルが大きくなったら、通常のコード分割ビルドに戻すのが素直な次の一手。

## ディレクトリ構成

```
src/
  types.ts               型定義（Stats, ScenarioNode, Choice, Ending など）
  data/
    chapter1.ts          第1章のシナリオデータ（本文はここ）
    chapter2.ts          第2章のシナリオデータ
    chapters.ts          章の登録簿（順番・ID検索）
    stats.ts             ステータスの表示名
  store/gameStore.ts     進行ロジック、条件判定、セーブ/ロード
  components/
    ChatScreen.tsx       画面全体の制御（逐次表示、選択肢、章の切り替え）
    MessageBubble.tsx    吹き出し1つ分の見た目
    StatusHUD.tsx        画面下部のステータス表示
  App.tsx / main.tsx     エントリーポイント
  index.css              LINE風UIのスタイル一式（ライト/ダーク両対応、話者ごとの地の色）
scripts/
  check-scenario.ts      シナリオの機械チェック（npm run check:scenario）
```

## シナリオを書き替えたら

```bash
npm run check:scenario
```

遷移先の実在・到達できないノード・reply の書き忘れを検査し、会話のつながり（選んだ内容 → 直後の返し → 次の本文）を全部書き出す。全ルートを総当たりして、各エンディングと条件つき選択肢に到達できるルートがあることも確認する。本文が噛み合っているかは、書き出された一覧を読んで判断する。
