# 人生（終盤）ゲーム ─ 全7章

介護・終活をテーマにした、LINE風メッセージ画面で進むノベルゲーム。
企画書の「開発ロードマップ W1: 土台構築」にあたる第1章（日常編）から、
第7章（相続編）まで、全7章を通しで遊べる。ステータスと、これまでの選択は章をまたいで引き継がれる。

## 遊び方

```bash
npm install
npm run dev
```

表示されるURL（通常 http://localhost:5173）をブラウザで開く。

## ビルド

```bash
npm run build
```

`dist/index.html` に、JS・CSSをすべて1ファイルに埋め込んだ自己完結型のHTMLが出力される（`vite-plugin-singlefile`を使用）。この1ファイルをそのままどこにでも置けば動く。

## 収録している章

| 章 | タイトル | 内容 |
| --- | --- | --- |
| 第1章 | 日常編 ── 「元気だよ」の一言から | 母からの何気ないLINE。息切れ、置き忘れ。まだ「歳のせい」で説明がつく |
| 第2章 | 予兆編 ── 「気のせい」が効かなくなる | 同じ話の繰り返し、空焚き、深夜の徘徊。隣人と兄が会話に入ってくる |
| 第3章 | 決断編 ── どれも、正解ではない | 診断、要介護認定、ケアマネジャー、お金。そして在宅か施設かを決める |
| 第4章 | 介護編 ── 続けるということ | 決めたあとの半年。ヘルパー、ショートステイ、兄との温度差、そして続けられるかどうか |
| 第5章 | 終活編 ── 話しておくべきこと | エンディングノート、通帳の在りか、実家の行方、医療の希望。父がはじめて口を開く |
| 第6章 | 看取り編 ── その日の決め方 | 誤嚥性肺炎での入院。どこまでの治療を行うかを、家族が決めることになる |
| 第7章 | 相続編 ── 遺されたもの | 手続き、実家の片付け、一人になった父。そして次は自分の番だと気づく |

エンディングは第2章が3種類、第3章・第4章・第6章が5種類ずつ、第5章と第7章が4種類ずつ。持ち越した「知識」「母との関係」
「きょうだいとの関係」、第3章では**どちらを選んだか**、第4章では**気力とお金が尽きていないか**が、
そのまま結末の分かれ目になる。

章の書き出しは前の章の終わり方で変わる。第3章は3通り（兄と向き合えたか、一人で抱えたか、
きっかけが外から来たか）、第4章は4通り（在宅／小規模多機能／施設待ち／決めないまま）、
第5章は5通り（前章の5つの結び方それぞれに対応）。

第5章はタイトルにある「終活」を初めて正面から扱う章で、**この章から結末の分かれ目がステータスではなくなる**。
母が話せるうちに何を聞けたか（お金の在りか／実家の行方／医療の希望）を3つのフラグで覚えていて、
持ち帰れた数と中身で結末が決まる。

そして第6章が、その差が効く章になる。**第5章で母の希望を聞けていた人だけ、医師と兄に「本人はこう言っていた」と
言える**（選択肢が解禁される）。聞けていない人は、本人の意思が分からないまま家族が決めることになり、
結末もそう書かれる。同じ主人公のまま、プレイヤーの選択の結果として両方を体験できるようにしてある。

第4章は「重いだけの話にしない」ことを意識して書いた。折り紙の鶴や昔の歌のような、
なんでもない明るさを必ず挟んでいる。介護は暗い一色ではなく、重さと軽さが同じ日に来るため。

## 学びのポイントと、感情の設計

この題材は「教材として正しいこと」と「遊んで面白いこと」が引っぱり合う。章ごとに**何を持ち帰ってほしいか**と**どんな感情を置くか**を分けて設計している。

| 章 | 学びのポイント | 置いている感情 |
| --- | --- | --- |
| 第1章 | （まだ何も起きない。基準値を作る章） | 何でもない日常。あとで効く |
| 第2章 | 地域包括支援センターは家族だけでも無料で相談できる／物忘れ外来 | 気づきかけて、打ち消す居心地の悪さ |
| 第3章 | 要介護認定の申請には1か月かかる／小規模多機能という第三の道 | どれを選んでも正解でない、という落ち着かなさ |
| 第4章 | ショートステイは家族が休むための制度／高額介護サービス費 | 折り紙の鶴。重さと軽さが同じ日に来る |
| 第5章 | エンディングノート／通帳の在りか／人生会議 | 父がはじめて口を開く。聞くほうがつらい |
| 第6章 | 医療者は決めてくれない。拠りどころは本人の言葉だけ | 「分かりません」と答えるしかない後悔 |
| 第7章 | 口座凍結と仮払い制度／相続の期限（3か月・10か月） | 既読がつかない画面。そして自分の番 |
| （全章共通） | 倒れる前にしか使えない制度がある | 「これを選ぶと気力が尽きる」と分かったうえで踏み出すかどうか |

**感情は作者が用意した泣かせ場ではなく、プレイヤー自身の選択の帰結から出す**、という方針をとっている。第6章で「分かりません」が刺さるとすれば、それは演出ではなく自分が聞かなかったからで、逆に第5章で聞いた人には別の結末が用意されている。

物語の山は第7章 n3 ──「母とのトークをもう一度開く」に置いた。最後のやり取りが残っていて、入力欄もあって、打てば送れて、既読だけがつかない。悲しみを書かずに、操作の結果として置いている。**このゲームの形式でしか書けない一点**を山にする、という判断。

## 何を・なぜこの設計にしたか

- **シナリオをコードから分離した（`src/data/chapter1.ts`, `chapter2.ts`）**
  ノード（発言のかたまり）と選択肢をデータとして定義し、エンジン（`src/store/gameStore.ts`）はそれを読んで進行を管理するだけにした。章を追加するときはデータファイルを1つ足し、`src/data/chapters.ts` の登録簿に並べて、前の章の `nextChapterId` を向けるだけでよい。UIやロジックには触らない。

- **「選んだ内容への返事」は選択肢側に持たせた（`choice.reply`）**
  最初は「選択肢 → 次のノード本文」しか無かったため、次のノードの1行目が特定の選択肢を前提にした返事になり、肯定的に答えたのに「あら、そうだった？」と返るような噛み合わない会話が生まれていた。いまは、選んだ内容に噛み合う返事はすべて選択肢の `reply` に置き、ノード本文はどの選択肢のあとに読んでも成立する内容だけにしている。**意思疎通が怪しくなる演出をやるときは、`reply` に意図してそう書く**（事故ではなく演出として出す）。この約束は `npm run check:scenario` で機械的に検査していて、`reply` の無い選択肢があると落ちる。

- **気力とお金が尽きると、そこで物語が止まる（`src/data/breakdown.ts`）**
  この2つは「使える手の数」そのものなので、ゼロになった時点で章の結末を待たずに中断する。第7章まで到達できない唯一の経路で、やり直すには章の頭に戻る。

  **尽きる選択肢を選べなくする案は捨てた。** 塞いでしまうと崖から落ちられなくなり、用意したバッドエンドに誰も到達しなかった（実測で第3章0.0%）。いまは塞がずに、**崖のほうを見せている** ── 「これを選ぶと気力が尽きる」と選択肢に出したうえで、選べるようにしてある。無理をすればできてしまうのが実際なので、踏み出すかどうかは本人が決める。

  実測すると、**警告を無視して選ぶと62.6%が途中で止まり、警告を見て避ければ95.1%が完走する**。警告が読まれているかどうかだけで結果が分かれる設計になっている。なお避けていても4.9%は止まる（節点の選択肢が全部崖になる＝本当に追い詰められた状態）。

  結びは罰として書かない。倒れるのも払えなくなるのも本人の努力不足ではなく支える手が足りなかった結果なので、「もっと早く頼れた」ほうを指す文章にしている。

  あわせて、**気力が落ちているときにしか出てこない選択肢**も置いた（兄に「もう限界かもしれない」と打ち明ける）。追い詰められて初めて助けを求められるようになる、という順序を条件の `max` で表している。

- **章の頭からやり直せる（`retryChapter`）**
  章に入った時点の状態を覚えておき、そこへ戻せるようにした。これが無いと、第6章で行き詰まったときに第1章からの再走になる。7章ぶんを繰り返させるのは罰として重すぎるので、尖ったバッドエンドを入れる前提条件として先に作った。

- **数字に写せない決断は、フラグで覚える（`choice.flags`）**
  第3章の「在宅で続けるか、施設を探し始めるか」は、ステータスの増減では表せない。選択肢に `flags` を立てて記録し、エンディングの条件（`condition.flags`）から参照している。第6章では逆に **立っていないこと**（`condition.notFlags`）も条件にしていて、「本人の意思を聞けないまま決めた」という、欠けていることが意味を持つ状況を書けるようにした。ステータスに無理やり写像すると「気力が減ったから在宅を選んだことにする」ような嘘の判定になるので、決断は決断として持たせた。フラグは章をまたいで持ち越され、綴り違いは `npm run check:scenario` が検出する（条件が見ているフラグを立てる選択肢が無いと落ちる）。

- **章の書き出しは、前の章の終わり方で変える（`chapter.prologue`）**
  `endings` と同じく、上から順に条件を判定して最初に成立したものを本文の前に差し込む。第3章の冒頭は、第2章のエンディング判定と同じ式で3通りに分かれる。同じ式を2か所に書くことになるが、結末と書き出しが食い違わないほうを取った。

- **エンディングもデータにした（`endings`）**
  第1章の時点では「bondMotherがしきい値以上か」をエンジン側にベタ書きしていたが、章ごとに結末が増えると破綻するので、`条件 → 結び` の配列として各章に持たせた。上から順に判定し、最初に条件を満たしたものを採用、条件を持たない最後の1件がフォールバックになる。分岐条件を読むのにコードを開かなくてよくなった。

- **選択肢に解禁条件をつけた（`requires`）**
  第2章の「地域包括支援センターに相談してみる」は、知識5以上でないと選べない。第1章から母の変化に気づいて言葉にしてきたプレイヤーにだけ道が開く、という設計。条件を満たしていない選択肢は消さずに、破線＋「知識 5 以上 で選べる」の一文で見せている。何を積めば違う結末に届くのかが、プレイ中に伝わるようにするため。

- **相手が変わると、新しいトーク画面が立ち上がる**
  第2章以降は隣の田中さん・兄・ケアマネジャーとのやり取りが挟まる。同じ相手との連続したやり取りをひとつのトーク画面とみなし、相手が変わったら画面ごと差し替える（右から立ち上がる）。ヘッダーの名前とアイコン、`tone` で指定した地の色も一緒に変わる。誰とやり取りしているのか見失わないようにするため。

  **前の画面の内容は持ち越さない。同じ人に戻ってきたときも、まっさらな画面から始まる**。実際のLINEなら過去ログが残るが、場面が変わったことを強く出すほうを取った（過去ログを追う画面は作っていない）。

  切り替えは自動では起きない。**別の相手からメッセージが来ると通知カードが出て進行が止まり**、タップすると新しいトークが開く。自動で切り替えていたときは、直前のやり取りを読み切る前に画面が変わってしまい、気持ちが追いつかなかった。カードがそのまま間になり、誰から来たのかも先に分かる。

  カードは**会話の末尾、選択肢が出るのと同じ位置**に、上から降りてくる。最初は画面上部に出していたが、最新の発言も選択肢もステータスも下にあるため視線と親指はすでに下にあり、上の通知は見落とされていた。降りてくる動きで「通知が来た」感じだけを残している。

  **進められるのは通知カードだけで、それ以外を触っても進まない**（カードを一度光らせて、押す場所を伝える）。どこを触っても進めるようにすると、早送りの手癖でタップした拍子に、読むために作った間を自分で飛ばしてしまうため。

  切り替えのタイミングは、現在ノードではなく **表示済みの最後のメッセージ** に追従させている（各メッセージが「誰との会話か」を持っている）。現在ノードを見てしまうと、選択肢をタップした瞬間に相手が変わり、自分の発言や母からの返事が、次の相手のトーク画面に表示されているように見えてしまうため。画面をタップしたときの早送りも、開いているトークの中だけにとどめている。

- **地の文のあとは、一拍置いてから次のメッセージが来る**
  メッセージの表示間隔は一律ではない。自分の発言は150ms、相手の発言は650ms、地の文どうしは850ms、そして**地の文のあとの最初の発言だけ1600ms**空けている。場面の前提を読む時間を作るため。待っているあいだは入力中のアニメーションが出続けるので、止まったようには見えない。逆に、地の文を待っているあいだは入力中を出さない（誰も打っていないため）。

- **数字はスロットのように回して止める（`StatusHUD`）**
  選択でステータスが動いたとき、桁ごとのリールが1周まわって左の桁から順に止まり、動いたぶんが「+3」「−8」と一瞬だけ数字の上に出る。**この選択が数字を動かした**と目で結びつけてもらうため。ストアは `choice.effects` ではなく前後の差（`lastDelta`）を渡していて、0や100で頭打ちになったときに動いていない数字を「+4」と表示してしまわないようにしている。読み込みや章の移動では演出を出さない（操作の結果ではないため）。アニメーションを切っている環境では、回さずに結果だけを出す。

- **地の色は白を使わない**
  画面の地を白にすると、相手の吹き出し（白）が地に溶けて境目が見えなくなる。地はどの場面でも少し色のついた紙にして、吹き出しを浮かせている。文字色のコントラストは主要な組み合わせを実測して決めた（小さい文字に使う暖色は、白地で3.05しか出ていなかったため4.87まで落としている）。

- **状態管理はZustand**
  `stats`（お金・気力・母/きょうだいとの関係値・知識）と `timeline`（表示済みメッセージ）、`chapterId` と `currentNodeId`（今どの章のどこにいるか）をシンプルなストアで一元管理している。

- **セーブはlocalStorageへ自動保存**
  選択するたびに`persist()`が状態をlocalStorageへ書き込む。サーバーもログインも不要で、ブラウザを閉じても続きから再開できる。章をまたぐ形式に変えたためキーは `jinsei-game-save-v2`。読み込み時に章IDとノードIDの実在を確認し、シナリオを書き替えたあとの古いセーブで詰まないようにしている。

  **復帰したときは、最後の状態から始まる。** 以前はセーブしたぶんのメッセージを1通ずつ再生し直していたが、続きから遊びたいだけの人に最初から見せ直すことになっていた。いまは復帰したぶんを「もう読んだ」扱いにして即座に表示し、場面の前置き（地の文）も出さない。復帰したあとに選んだぶんは、いつもどおり1通ずつ表示される。

- **ビルドを1ファイルに固めた（vite-plugin-singlefile）**
  MVPの段階では「どこでもすぐ動かせる」ことを優先。章が増えてバンドルが大きくなったら、通常のコード分割ビルドに戻すのが素直な次の一手。

## シナリオを書き替えたら

```bash
npm run check:scenario
```

遷移先の実在・到達できないノード・reply の書き忘れ・フラグの綴り違いを検査し、会話のつながり（選んだ内容 → 直後の返し → 次の本文）を全部書き出す。各エンディング・各書き出し・条件つき選択肢に到達できるルートがあることも確認する。本文が噛み合っているかは、書き出された一覧を読んで判断する。

### なぜ全組み合わせを数え上げないか

最初は章をまたいだ全ルートを数え上げていたが、この方針は第3章で破綻した。

| | 章の中のルート数（開始状態1つあたり） | 章の終了時点で互いに異なる状態の数 |
| --- | --- | --- |
| 第1章 | 27 | 24 |
| 第2章 | 1,863 | 37,221 |
| 第3章 | 729 | （ノード×状態が数千万を超え、重複排除しても6GBで足りない） |

**章の中のルート数は多くても2000程度で、まったく問題ない。伸びているのは章をまたぐ組み合わせのほうだけ**、というのがこの表の読み方になる。間引いて誤魔化すこともできるが、それでは全数検査ではなく標本検査になるうえ、章が増えれば結局行き詰まる。

そこで、**前の章をどう終えたかを代表的な状態に絞り、各章はその代表ごとに全数探索する**方式にした。代表に選ぶのは、各ステータスの最大・最小、2つの組み合わせの最大（「知識8以上かつ関係53以上」のように条件が重なるため）、前章のエンディングごと・フラグの組み合わせごとに1件。第3章時点で21通りになる。

ステータスの増減は足し算なので、最大値・最小値を持つ状態を代表に入れておけば「どこまで伸ばせるか／どこまで落ちるか」は代表からでも見える。実際、この方式で出したステータスの到達範囲は、全数検査していたときの値と一致した（第3章末で `energy 0〜70` / `knowledge 0〜27`）。実行時間は2分28秒から0.4秒になり、章を足しても線形にしか増えない。

ただし、エンディングに到達できないと報告された場合は「代表状態からは見つからなかった」の意味になる。到達できると報告されたものは実在のルートなので、そちらは確実。

### バランスの目安

代表状態からのルート数の割合は、極端な状態が多めに混ざるため実際のプレイ感とずれる。そこで検査の最後に、**選択肢を等確率で選ぶ通しプレイを2万回**繰り返した分布も出している（人は等確率では選ばないので、これも真の確率ではなく、傾きを見るための目安）。

これを見ながら閾値を調整した。たとえば第4章の `ひとりで抱えない形ができた` は、当初の条件（知識24かつきょうだい55）では2万回中0回で、意図した「報われる結末」が誰にも届いていなかった。

同じ測定で、**すべて「正しく」選んだプレイヤーがお金を使い果たして `お金が続かない` に落ちる**ことも分かった。向き合うほど出費が増える構造そのものはリアルだが、調べた人が金銭的に追い詰められて終わるのは設計として逆なので、知識で抜け道を作った（第3章に高額介護サービス費の選択肢を追加）。
